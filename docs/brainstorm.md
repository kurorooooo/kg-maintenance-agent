# 設備保全ナレッジグラフ＋保全エージェント デモ要件定義

Oct 4, 2026 · @kakeru kurosawa

大手製造業向けデモとして、設備・部品・故障モード・過去対応をつないだ小さなナレッジグラフをNeo4jに作り、MCP経由でClaudeが根拠パス付きで保全質問に答える構成を、合成データ中心に5日で作る。

## 目的とゴール

このデモの目的は、大手製造業の保全・DX部門に「社内の設備情報と過去の対応履歴をグラフ化すると、根拠付きで答えるAIエージェントが短期間で作れる」ことを10分で体感してもらうこと。

**証明したいこと（3点）**

1. 多段の関係（設備 → 部品 → 故障モード → 過去対応 → 担当者）をAIが辿って答えられる。RAGだけでは「別ラインの同型機の事例」のような横断質問に弱い点との差を見せる
2. 回答の根拠がグラフ上のパスとして可視化され、幻覚ではないことを人が検証できる
3. 手元のマニュアルPDFや作業報告からナレッジグラフを数日で作れる（AIdeaLabの受託で再現可能）

**ターゲット**：大手製造業の設備保全部門、生産技術部門、DX推進部門。商談の初回〜2回目で見せる想定。

**成功条件**

| 条件 | 判定方法 |
| --- | --- |
| 代表質問4問すべてに正しい根拠パス付きで答える | 事前に正解パスを定義し、デモ前にリハーサルで確認 |
| 1問あたりの応答が10秒以内 | Claude側の応答時間を計測 |
| グラフ可視化で「自分の現場の構造だ」と相手が言う | デモ後のヒアリングで確認 |
| 顧客の社内データで同じものを作る次のステップを提案できる | デモ資料の最後に「御社データでの構築手順（2〜4週間）」を1枚入れる |

## デモシナリオ

想定ユーザーは工場の保全担当者。夜間に異常が出て、ベテランが不在の場面を設定する。架空の工場「A工場」の3ライン・12設備を舞台にする。

**代表質問と見せ場**

| # | 質問 | エージェントが辿るパス | 見せ場 |
| --- | --- | --- | --- |
| 1 | 3号ラインの冷却ポンプP-301で振動が上がっている。考えられる原因と過去の対処は？ | Equipment → Component → FailureMode ← Symptom、FailureMode → WorkOrder → Procedure | 症状から故障モードを絞り、過去の作業報告と手順書を根拠に答える |
| 2 | 同じ型式のポンプで同じ症状が出た事例は他ラインにもある？ | Equipment → Model ← Equipment → WorkOrder → FailureMode | ライン横断の類似事例検索。RAG単独では出にくい質問 |
| 3 | その対処に必要な部品の在庫と納期、対応できる技術者は？ | Procedure → Part → Supplier、Procedure ← WorkOrder → Technician | 対処の「次の行動」まで一気通貫で答える |
| 4 | 直近1年でベアリング起因の停止が多い設備はどこ？ | FailureMode ← WorkOrder → Equipment を集計 | 集計系の質問もグラフで答えられることを示す |

**進行（約10分）**

1. グラフモデルの絵を1枚見せ、「御社の設備台帳・作業報告・マニュアルをこの形につなぐ」と説明（1分）
2. Neo4jブラウザでP-301周辺のサブグラフを表示し、構造を直感で理解してもらう（1分）
3. 質問1〜3を順に投げ、回答と根拠パスの可視化を並べて見せる（6分）
4. 質問4で集計を見せ、最後に「御社データでの構築手順」を1枚で提示（2分）

質問1で手順書のチャンクを根拠として引用させ、「マニュアルのこのページから来ている」と出典を示すところが最大の見せ場。

## スコープ

MVPは「合成データで4つの代表質問に答える」ところまでに絞る。センサー時系列や予知保全は含めない。

| 含む（MVP） | 含まない（次フェーズ候補） |
| --- | --- |
| 架空のA工場：3ライン、12設備、約40部品、約25故障モード、約80件の作業報告 | センサー時系列データ（NASA C-MAPSS等）を使った異常検知・予知 |
| 手順書3〜5本（合成テキスト、各2〜4ページ相当）のチャンク化とベクトル検索 | 実在顧客データの取り込み |
| mcp-neo4j-cypher 経由でClaudeがCypherを実行し回答 | 独自Webチャット画面（MVPはClaude Desktopかclaude.aiで代替） |
| 根拠パスのNeo4jブラウザ表示 | 作業報告の自動登録（書き込み系エージェント） |
| 質問テンプレート4本と期待回答の定義 | 多言語対応、音声入力 |
| 読み取り専用ロールでの接続 | SSO・監査ログ等の本番セキュリティ |

## データ要件

MVPのデータはすべて合成（Pythonで生成）とし、機密・ライセンスの問題をゼロにする。実在メーカー名・型式は使わない。

| データ | 生成方法 | 件数目安 | 主な項目 |
| --- | --- | --- | --- |
| ライン・設備台帳 | 手書きCSV | 3ライン、12設備 | 設備ID（P-301等）、名称、型式、設置年、ライン |
| 型式・部品構成 | 手書きCSV | 5型式、約40部品 | 型式、部品名、部品番号、交換周期、在庫数、標準納期 |
| 故障モード・症状 | 手書きCSV | 約25故障モード、約15症状 | 故障モード名、対象部品、典型症状、緊急度 |
| 対処手順 | 手書きCSV＋Claudeで本文生成 | 約20手順 | 手順名、所要時間、必要部品、必要資格 |
| 作業報告（Work Order） | Pythonで故障モード・設備・技術者をランダムに組み合わせて生成 | 約80件（直近2年） | 日付、設備、症状、診断した故障モード、実施手順、技術者、停止時間 |
| 技術者 | 手書きCSV | 6名 | 氏名（架空）、所属ライン、保有資格 |
| サプライヤー | 手書きCSV | 4社（架空） | 社名、担当部品、標準納期 |
| 手順書（マニュアル） | Claudeで合成テキストを生成しMarkdown化 | 3〜5本 | 設備ごとの点検・交換手順、注意事項。チャンク化してベクトル索引 |

**作業報告の分布設計**：質問2・4が面白くなるよう、同一型式のポンプが別ラインで同じ故障モードを繰り返している、ベアリング起因の停止が特定設備に偏っている、という「気づき」を意図的に埋め込む。

**オープンデータの位置づけ**：MVPでは使わない。次フェーズでNASA C-MAPSSのセンサー劣化データを設備ノードに紐づけ、「振動トレンドから故障モードを予測して手順を提案」まで拡張する余地を残す。

## グラフモデル

&#91;embedded content: グラフモデル · 12ノード・14リレーション\]

故障モード（FailureMode）がハブになる。症状から故障モードへ入り、部品・型式を経由して同型機へ横断し、作業報告と対処手順で過去の対応に降り、交換部品からサプライヤーまで辿る。手順書チャンクは部品と故障モードに紐づき、GraphRAGの起点兼根拠になる。

**主なプロパティ**

| ノード | プロパティ | 制約・インデックス |
| --- | --- | --- |
| Equipment | id（P-301）、name、installedYear | id に NODE KEY |
| Component | id、name、partNo、replaceCycleMonths | id に NODE KEY |
| FailureMode | id、name、severity | id に NODE KEY、name に TEXT インデックス |
| Symptom | id、name（振動増大、異音、温度上昇…） | name に一意制約 |
| WorkOrder | id（WO-2025-031）、date、downtimeMin、note | id に NODE KEY、date に range インデックス |
| Procedure | id、name、durationMin、requiredCert | id に NODE KEY |
| Part | id、name、stockQty、leadTimeDays | id に NODE KEY |
| Chunk | id、text、embedding（1,536次元）、source、page | embedding にベクトルインデックス |

## システム構成

&#91;embedded content: システム構成 · 7コンポーネント\]

左半分がデモ中に動く経路（担当者 → Claude → MCP → Neo4j）、右半分が事前準備の経路（データ生成と埋め込み → Neo4j）。発表者はClaudeの回答とNeo4jブラウザの根拠パスを並べて見せる。自作コードはデータ生成と埋め込み投入のスクリプトのみで、残りは既製品の組み合わせ。

## エージェント要件

エージェントはClaude（Claude DesktopまたはClaude.aiのMCPコネクタ）とし、Neo4jにはMCP経由で読み取り専用アクセスする。独自ツールは最小限にし、まずは標準MCPサーバーだけで成立させる。

**ツール構成**

| ツール | 提供元 | 役割 |
| --- | --- | --- |
| get\_schema | mcp-neo4j-cypher | ラベル・リレーション・プロパティを取得し、Cypher生成の前提にする |
| read\_cypher | mcp-neo4j-cypher | 読み取りCypherの実行。書き込み系は無効化 |
| search\_manual | 自作（Phase 2、任意） | 症状テキストをベクトル索引で検索し、該当チャンクとそのチャンクがMENTIONSする部品・故障モードを返す。MVPではread\_cypherから db.index.vector.queryNodes を直接呼んで代替 |

**システムプロンプトの方針**

- 役割：A工場の保全アシスタント。必ずグラフを参照してから答え、グラフにない情報は「記録なし」と言う
- 回答手順：(1) 症状・設備名から起点ノードを特定、(2) 故障モード候補と過去の作業報告を取得、(3) 手順書チャンクで裏付け、(4) 次の行動（部品・技術者）を提示
- 根拠の提示：回答末尾に「根拠」節を置き、使った作業報告ID、手順ID、手順書チャンクID、辿ったパスを箇条書きで列挙する。パスは `P-301 → ベアリング → 内輪摩耗 → WO-2025-031` の形式
- 禁止：グラフにない部品番号や納期を作らない、1クエリで取れない集計を推測しない

**回答フォーマット（固定）**

1. 結論（1〜2文）
2. 原因候補（確度順、各1行に根拠となる過去事例数）
3. 推奨対処と必要な部品・技術者
4. 根拠（ID列挙とパス）

**根拠パスの可視化**：回答に含まれるIDを使い、Neo4jブラウザで `MATCH p = (e:Equipment {id:'P-301'})-[*1..3]-(w:WorkOrder {id:'WO-2025-031'}) RETURN p` 相当のクエリをあらかじめ用意して並べて表示する。MVPでは手動切り替え、Phase 2でパスをクリック可能にする。

**評価**：代表質問4本ごとに期待する起点ノード・故障モード・作業報告IDを定義し、5回実行して4回以上一致すれば合格とする。

## 非機能要件

| 項目 | 要件 | 根拠・備考 |
| --- | --- | --- |
| 応答時間 | 1質問あたり10秒以内（Cypher実行は1秒以内） | デモ中に間延びさせない。設備ID・故障モード名にインデックスを張る |
| 説明可能性 | 全回答に根拠ID列挙とパス表記を必須化 | デモの価値そのもの。根拠のない回答は不合格扱い |
| 再現性 | 代表質問4本で5回中4回以上同じ結論 | デモ前日にリハーサルで確認。温度設定は低めに固定 |
| セキュリティ | エージェント用ユーザーは読み取り専用ロール（MATCH権限のみ、書き込み権限なし）。手順書に機密を含めない | 第6章の最小権限原則。合成データのみなので情報漏洩リスクは実質ゼロ |
| 可搬性 | Docker Composeで1コマンド起動、またはAura Freeで即時再現 | 営業メンバーが自分のPCでも見せられるように |
| データ規模 | ノード約300、リレーション約1,000、チャンク約100 | Aura Free（上限20万ノード・40万リレーション）で十分 |
| コスト | Neo4j Aura Free 0円、Claude利用料のみ | 月数千円規模。社内アカウントで運用 |
| 保守 | 合成データ生成スクリプトとCypher投入スクリプトをリポジトリで管理 | データを変えたくなったときに再生成できる |

## 実装ステップ（5日間）

1人で5日、または2人で3日を想定。各日の終わりに動くものがある状態を保つ。

| 日 | 作業 | 成果物 | 完了条件 |
| --- | --- | --- | --- |
| 1 | グラフモデル確定、合成データのCSV作成（台帳・部品・故障モード・手順・技術者・サプライヤー） | model.md、data/\*.csv | 代表質問4本の正解パスがCSV上で追えること |
| 2 | 作業報告の生成スクリプト、Neo4j起動（Docker ComposeまたはAura Free）、制約・インデックス作成、LOAD CSVでの投入 | gen\_workorders.py、load.cypher | ブラウザでP-301周辺のサブグラフが表示できること |
| 3 | 代表質問4本をCypherで手書きし正解を確認、読み取り専用ユーザー作成、mcp-neo4j-cypherをClaudeに接続 | queries.cypher、MCP設定 | Claudeが質問1〜4に根拠ID付きで答えること |
| 4 | 手順書の合成テキスト生成、チャンク化と埋め込み、ベクトルインデックス作成、ChunkとComponent/FailureModeの紐づけ | manuals/\*.md、embed.py | 質問1で手順書チャンクが根拠に引用されること |
| 5 | システムプロンプト調整、根拠パス可視化クエリの用意、リハーサル5回、デモ台本と「御社データでの構築手順」1枚作成 | prompt.md、demo\_script.md、paths.cypher | 成功条件の表をすべて満たすこと |

**担当の目安**：1〜2日目はデータ設計ができる人、3〜5日目はClaudeのプロンプト調整ができる人。両方を1人で担う場合は2日目までにPM側にデータの筋をレビューしてもらうと、後半の手戻りが減る。

**次フェーズ（デモ後、2〜4週間）**：顧客の設備台帳・作業報告・マニュアル実データでの再構築、LLM Knowledge Graph Builderによるマニュアルからのエンティティ抽出、センサー時系列の接続、Webチャット画面と根拠パスのクリック表示。

## 未決事項とリスク

**未決事項**

- [ ] Neo4jの稼働先：ローカルDocker（可搬性）かAura Free（セットアップ不要）か。デモ会場のネットワーク次第で決める
- [ ] Claude側の入口：Claude Desktop（MCP設定が簡単）かclaude.aiのカスタムコネクタ（営業が共有しやすい）か
- [ ] 手順書の埋め込みモデル：OpenAI text-embedding-3-small を使うか、ローカル埋め込み（オンプレ訴求のため）にするか
- [ ] 設備の業種設定：汎用的な「ポンプ・コンベア・プレス」にするか、初回商談先の業種（自動車部品、化学プラント等）に寄せるか
- [ ] デモ用の見た目：Neo4jブラウザのままか、Bloom／NeoDashで整えるか

**リスク**

| リスク | 影響 | 対策 |
| --- | --- | --- |
| ClaudeがCypher生成で失敗し、デモ中に答えられない | 信頼性の印象を損なう | 代表質問4本は事前にCypherを検証し、システムプロンプトにクエリ例を含める。リハーサルを5回実施 |
| 合成データが「作り物」に見える | 自分事化されない | 作業報告の文面を現場の言い回しに寄せ、故障モードの偏りなど「発見」を埋め込む |
| 相手から「うちのデータは紙・Excelで整っていない」と言われる | 導入イメージが湧かない | 次フェーズの手順でLLM Knowledge Graph Builderによる非構造データ取り込みを示す |
| ベクトル検索と構造検索の使い分けが説明しづらい | 技術的な質問で詰まる | 「ベクトルで起点を見つけ、グラフで文脈を辿る」の1枚図を用意する |
| 回答が10秒を超える | 間延び | インデックス整備、プロンプトの短縮、質問ごとのツール呼び出し回数を3回以内に抑える |
