# 要件定義書：設備保全ナレッジグラフ＋保全エージェント デモ

- 作成日：2026-10-04
- 元資料：docs/brainstorm.md（ブレスト版）、docs/decisions.md（未決事項の決定）
- 関連：docs/model.md（グラフモデル）、docs/architecture.md（システム構成）、docs/tasks.md（進捗）

## 1. 背景と目的

大手製造業の保全・DX部門に対し、「社内の設備情報と過去の対応履歴をグラフ化すると、根拠付きで答えるAIエージェントが短期間で作れる」ことを10分で体感してもらう商談用デモ。合成データのみを使い、5日で構築する。

### 証明したいこと

1. 多段の関係（設備 → 部品 → 故障モード → 過去対応 → 担当者）をAIが辿って答えられる。RAG単独では弱い「別ラインの同型機の事例」のような横断質問に答えられる。
2. 回答の根拠がグラフ上のパスとして可視化され、幻覚でないことを人が検証できる。
3. 手元のマニュアルや作業報告からナレッジグラフを数日で作れる（受託で再現可能）。

### ターゲット

大手製造業の設備保全部門、生産技術部門、DX推進部門。商談の初回〜2回目で提示する。

## 2. 成功条件

| 条件 | 判定方法 |
| --- | --- |
| 代表質問4問すべてに正しい根拠パス付きで答える | docs/model.md の正解パスと照合。デモ前にリハーサル5回中4回以上一致 |
| 1問あたりの応答が30秒以内（当初10秒。実測 37〜71 秒を踏まえ見直し提案中） | Claude Desktop での応答時間を計測。Cypher 単体は1秒以内（実測 35〜170ms） |
| グラフ可視化で「自分の現場の構造だ」と相手が言う | デモ後ヒアリング |
| 顧客データで同じものを作る次のステップを提案できる | デモ資料末尾に「御社データでの構築手順（2〜4週間）」を1枚入れる |

## 3. デモシナリオ

想定ユーザーは架空の「A工場」の保全担当者。夜勤帯に異常が出てベテラン（佐伯）が不在、という場面。

### 舞台：A工場

| ライン | 工程 | 設備 |
| --- | --- | --- |
| 第1ライン | プレス | PR-101、PR-102（プレス機）、P-101（冷却ポンプ CP-200）、CV-101（搬出コンベア） |
| 第2ライン | 搬送 | CV-201、CV-202、CV-203（コンベア）、P-201（冷却ポンプ CP-200） |
| 第3ライン | 冷却ユーティリティ | P-301、P-302（冷却ポンプ CP-200）、CT-301（冷却塔）、AC-301（エアコンプレッサ） |

同型の冷却ポンプ CP-200 を全ラインに置き、「別ラインの同型機」の横断質問を成立させる。

### 代表質問

| # | 質問 | 辿るパス | 見せ場 |
| --- | --- | --- | --- |
| 1 | 3号ラインの冷却ポンプ P-301 で振動が上がっている。考えられる原因と過去の対処は？ | Equipment → Model → Component → FailureMode ← Symptom、FailureMode ← WorkOrder、Procedure → FailureMode、Chunk → FailureMode | 症状から故障モードを絞り、過去の作業報告と手順書チャンクを根拠に答える。手順書の出典ページを示すのが最大の見せ場 |
| 2 | 同じ型式のポンプで同じ症状が出た事例は他ラインにもある？ | Equipment → Model ← Equipment ← WorkOrder → FailureMode | ライン横断の類似事例検索 |
| 3 | その対処に必要な部品の在庫と納期、対応できる技術者は？ | Procedure → Part → Supplier、Procedure ← WorkOrder → Technician、Technician.cert | 次の行動まで一気通貫 |
| 4 | 直近1年でベアリング起因の停止が多い設備はどこ？ | FailureMode{category:bearing} ← WorkOrder → Equipment を集計 | 集計系もグラフで答える |

### 進行（約10分）

1. グラフモデルの絵を1枚見せる（1分）
2. Neo4j Browser で P-301 周辺のサブグラフを表示（1分）
3. 質問1〜3を順に投げ、回答と根拠パスを並べて見せる（6分）
4. 質問4で集計を見せ、「御社データでの構築手順」を提示（2分）

### 作業報告の分布設計（意図的な「気づき」）

- CP-200 型ポンプの主軸ベアリング内輪摩耗（FM-001）が P-301 と P-101 で繰り返し発生（質問2）
- ベアリング起因の停止時間が P-301 と CV-201 に偏る（質問4）
- P-301 は再発間隔が短くなっており、作業報告 note にその旨の現場コメントがある（質問1の深み）

## 7. システム構成

docs/architecture.md を正とする。要点：

- Neo4j 5.26 Community を Docker Compose で起動（ポート 7474 / 7687）
- Claude Desktop と Claude Code から mcp-neo4j-cypher（読み取り専用モード）経由で接続
- 自作 MCP サーバー mcp/search_manual で multilingual-e5-small による質問文の埋め込みとベクトル検索を提供
- 自作コードはデータ生成、投入、埋め込み、search_manual の4スクリプトのみ

## 8. エージェント要件

### ツール

| ツール | 提供元 | 役割 |
| --- | --- | --- |
| get_neo4j_schema | mcp-neo4j-cypher | ラベル・リレーション・プロパティを取得 |
| read_neo4j_cypher | mcp-neo4j-cypher | 読み取り Cypher の実行。write ツールは読み取り専用モードで無効 |
| search_manual | 自作（mcp/search_manual） | 症状テキストを埋め込みベクトル化し、該当チャンクとそのチャンクが MENTIONS する部品・故障モードを返す |

### システムプロンプトの方針

- 役割：A工場の保全アシスタント。必ずグラフを参照してから答え、グラフにない情報は「記録なし」と言う
- 手順：(1) 症状・設備名から起点ノードを特定、(2) 故障モード候補と過去の作業報告を取得、(3) 手順書チャンクで裏付け、(4) 次の行動（部品・技術者）を提示
- 根拠：回答末尾に「根拠」節を置き、作業報告ID、手順ID、チャンクID、辿ったパスを列挙。パスは `P-301 → 主軸ベアリング → 主軸ベアリング内輪摩耗 → WO-2026-012` の形式
- 禁止：グラフにない部品番号や納期を作らない、1クエリで取れない集計を推測しない
- ツール呼び出しは1質問あたり3回以内

### 回答フォーマット（固定）

1. 結論（1〜2文）
2. 原因候補（確度順、各1行に過去事例数）
3. 推奨対処と必要な部品・技術者
4. 根拠（ID列挙とパス）

### 評価

代表質問4本ごとに期待する起点ノード・故障モード・作業報告IDを定義し、5回実行して4回以上一致で合格。

## 9. 非機能要件

| 項目 | 要件 | 備考 |
| --- | --- | --- |
| 応答時間 | 1質問30秒以内（提案）、Cypher 1秒以内 | ツール呼び出し3回以内、回答400〜700字、search_manual はモデル先読み。10秒はエージェント型（検索→Cypher→回答）では非現実的 |
| 説明可能性 | 全回答に根拠IDとパス表記を必須化 | 根拠のない回答は不合格 |
| 再現性 | 代表質問4本で5回中4回以上同じ結論 | デモ前日にリハーサル |
| セキュリティ | MCP 読み取り専用モード。手順書に機密を含めない | Community 版のため DB ロールは使わない |
| 可搬性 | `docker compose up` と `python scripts/load.py` で再現 | 営業メンバーの PC でも見せられる |
| データ規模 | ノード約300、リレーション約1,000、チャンク約100 | |
| コスト | Neo4j Community 0円、埋め込みローカル 0円、Claude 利用料のみ | |
| 保守 | 生成・投入・埋め込みスクリプトをリポジトリ管理 | データ変更時に再生成できる |

## 11. リスク

| リスク | 影響 | 対策 |
| --- | --- | --- |
| Claude が Cypher 生成で失敗 | 信頼性の印象を損なう | 代表質問4本の検証済み Cypher をシステムプロンプトに例示。リハーサル5回 |
| 合成データが「作り物」に見える | 自分事化されない | 作業報告の文面を現場の言い回しに寄せ、故障の偏りなど「発見」を埋め込む |
| 「うちのデータは紙・Excel」と言われる | 導入イメージが湧かない | 次フェーズで LLM Knowledge Graph Builder による非構造データ取り込みを示す |
| ベクトル検索と構造検索の使い分けが説明しづらい | 技術質問で詰まる | 「ベクトルで起点を見つけ、グラフで文脈を辿る」の1枚図（architecture.md） |
| 回答が10秒を超える | 間延び | インデックス整備、プロンプト短縮、ツール呼び出し3回以内 |
| search_manual のモデル初回ロードが遅い | デモ冒頭で待たされる | デモ前に一度ウォームアップ質問を投げる |
